# DEYE Control PWA

**Відкрити на телефоні: https://ostapfed.github.io/deye-control-pwa/**

Мобільний PWA українською з погодженою іконкою DEYE. Працює у демонстраційному режимі або як клієнт локального сервера з каталогу `gateway/`.

## Функції

- Поточні потужності: генерація, навантаження, імпорт, експорт, пряме живлення будинку від сонця, заряд/розряд батареї.
- Енергія за 24 години, 7 і 30 днів: генерація, експорт, пряме сонячне споживання та імпорт, графіки, CSV.
- Кілька батарей: номінальна ємність у кВт·год, доступна частка у %, сумарна розрахункова ємність.
- Мінімальний і цільовий SOC у %, прогноз до планового ввімкнення, таймери та ручний графік своєї групи.
- Команди інвертора із серверного дозволеного списку: межі, крок, підтвердження, контрольне читання та журнал.
- Профіль Modbus TCP можна налаштувати у вкладці «Зв’язок» після входу на сервер.
- PWA, мобільна навігація, офлайн-оболонка. Демо працює офлайн; остання реальна телеметрія зберігається в поточній сесії браузера, позначається застарілою, команди блокуються.

У режимі **«Демо» всі показники й команди синтетичні**. Перемикання сценаріїв не керує обладнанням. Публічний GitHub Pages не є сервером інвертора і не виконує Python.

## Встановлення

iPhone: Safari → Поділитися → На початковий екран. Android: меню Chrome → Встановити додаток. Для оновлення старого ярлика iOS іноді потрібно видалити його та додати знову. Іконка — білий DEYE із зеленою блискавкою.

## Реальне підключення

1. Клонуйте цей репозиторій на комп’ютер або Raspberry Pi, який постійно працює біля інвертора. Python 3.10+. Modbus TCP працює без сторонніх пакетів; для Solarman V5 встановіть `python -m pip install -r gateway/requirements.txt`.
2. Задайте приватний пароль сервера та запустіть:

```bash
export DEYE_PASSWORD='замініть-на-унікальний-пароль-від-12-символів'
export DEYE_WEB_ORIGINS='https://ostapfed.github.io'
python3 gateway/app.py
```

Windows PowerShell:

```powershell
$env:DEYE_PASSWORD='замініть-на-унікальний-пароль-від-12-символів'
$env:DEYE_WEB_ORIGINS='https://ostapfed.github.io'
python gateway/app.py
```

3. Сервер слухає 127.0.0.1:8080. Відкрийте локально http://127.0.0.1:8080 або організуйте HTTPS через свій reverse proxy/VPN. PWA на GitHub Pages може підключатися до HTTPS-сервера. Звичайний HTTP на IP Raspberry Pi не підходить через mixed content і вимоги PWA. Не виставляйте порт Modbus чи незахищений HTTP у публічний інтернет.
4. У PWA «Зв’язок» → «Реальний локальний сервер», вкажіть HTTPS-адресу та пароль. Пароль зберігається лише в пам’яті вкладки, не в localStorage і не в GitHub. Після перезавантаження введіть його знову.
5. Розгорніть «Профіль підключення до інвертора на сервері». Вкажіть Modbus TCP-шлюз, Unit ID і перевірену карту регістрів своєї моделі та прошивки. Збережіть профіль. Сервер за замовчуванням у деморежимі; його демопоказники не вважаються реальним зв’язком.
6. Після успішної перевірки реальної телеметрії вкладка «Інвертор» покаже параметри `writable` з профілю, якщо увімкнено «Карта перевірена» та «Дозволити запис».

`DEYE_BIND` і `DEYE_PORT` налаштовують адресу/порт сервера. `DEYE_DATA` — приватний каталог даних (типово `gateway/data/`, виключений з Git). `DEYE_WEB_ORIGINS` — точний список дозволених веб-origin через кому, без шляхів. Для локальної панелі CORS не потрібен.

### Карта регістрів

Готову карту Deye без перевірки моделі/прошивки тут навмисно не встановлено. Конкретний логер Solarman може використовувати V5 замість стандартного Modbus TCP. **Хмарний Solarman API, USB/RS485 без TCP-шлюзу, 32-бітні та бітові поля наразі не підтримано.** Solarman V5 підтримується через pysolarmanv5 3.0.6; необхідні SN логера та встановлення залежностей. Для них треба додати й перевірити драйвер.

Мінімальні канали:

| Ключ | Значення |
|---|---|
| `soc` | SOC у %, 0–100 |
| `pv_w` | Генерація, Вт |
| `load_w` | Навантаження, Вт |
| `grid_on` | Мережа є: 1, немає: 0; окремий регістр, не маска |
| `grid_import_w` | Імпорт із мережі, Вт, невід’ємний |
| `grid_export_w` | Експорт у мережу, Вт, невід’ємний |
| `solar_direct_w` | Пряме живлення навантаження від сонця, Вт |
| `battery_w` | Батарея: додатне — заряд, від’ємне — розряд, Вт |

Останні чотири канали необов’язкові. Без них відповідні показники будуть «—», а не вигаданими нулями. Якщо інвертор не видає пряме сонячне споживання, потрібен окремий перевірений розрахунок потоків; просте «генерація мінус експорт» включає заряд батареї й втрати та не тотожне споживанню будинку.

Один елемент JSON-профілю має поля `address` (число з документації), `function` (3 або 4), `scale` (множник), `signed` (true/false). Реєстр 16-бітний. Для команди додайте `writable: true`, `min`, `max`; необов’язково `label` і `unit`. Запис — FC06. Не підставляйте прикладні чи випадкові адреси: для реального інвертора потрібна його документація.

Командні ключі довільні. Якщо ключі меж SOC названі `reserve_soc` і `target_soc`, сервер також перевіряє їхню узгодженість і оновлює розрахункові межі після підтвердженого запису. Кодування режимів роботи та часові розклади залежать від моделі. Складені багаторегістрові меню не реалізовані універсально.

### Батареї та відсотки

Номінальна ємність — фізична характеристика в кВт·год. Доступна частка у % — поправка для моделі запасу енергії; вона не змінює фізичну ємність і не перепрограмовує BMS. Доступна ємність банку = сума `nominal_kwh × usable_pct / 100`. Мінімальний SOC і цільовий SOC — інші параметри. Вкладка «Батареї» зберігає їх для прогнозу, а реальну зміну регістрів виконуйте окремо у «Інвертор».

Відображається загальний SOC від BMS. Окремі рівні заряду модулів без телеметрії цих модулів не вигадуються. Для прогнозу використовується ККД 90%, сталі потужності й консервативне припущення без майбутнього заряду від мережі. Майбутня погода не прогнозується.

### Облік електроенергії

Реальні кВт·год інтегруються з потужностей, записаних сервером типово раз на 2 секунди. Пропуски понад 120 секунд не інтегруються. Показано загальне покриття та покриття кожного каналу. Немає ретроспективних даних до початку збору. Це облік вимірювань, а не офіційний розрахунковий лічильник.

Демо- і реальні вимірювання не змішуються у звіті. Зберігається до 90 днів. Сервер повертає погодинні середні для графіка та CSV панелі; `/api/history.csv` містить усі сирі збережені точки. Власне сонячне споживання показує тільки прямий потік; походження розряду батареї не обліковується. Демо-звіти — синтетичний профіль для перевірки інтерфейсу, а не історія користувача.

### Графіки, Telegram, захист

Адреса та група задаються вручну; автоматичного пошуку групи за адресою немає. Графік — JSON-масив об’єктів `group`, `start`, `end`, дати ISO 8601 із `Z` або зсувом `+02:00`. Перекриті/суміжні інтервали об’єднуються. Графік не гарантує фактичних вимкнень.

Для Telegram задайте серверу `TELEGRAM_BOT_TOKEN`, а в приватному серверному config.json — `telegram_users` (числові ID). Команди `/status`, `/schedule`, `/report`, `/set назва значення` та `/confirm код`. Автоматичні повідомлення про мережу, зв’язок, планові відключення й резерв працюють лише в реальному режимі сервера. Роутер та комп’ютер повинні залишатися під живленням.

Реальні записи виконуються лише з паролем, перевіреним профілем і явним дозволом. Перевіряються діапазон і крок, виконується контрольне читання, спроба/результат фіксуються в SQLite. Багатопараметрових атомарних змін немає. Паролі не ставляться в офлайн-чергу, команди не відправляються автоматично після відновлення мережі. Service worker кешує тільки статичні файли, API виключено.

## Real-time та кілька домогосподарств

Поточні показники передаються сервером через авторизований SSE-потік (`/api/stream`) приблизно кожні 2 секунди. Період опитування Modbus `poll_seconds` — 2–60 с, типово 2 с. Повільний шлюз може збільшити фактичну затримку. Для HTTPS reverse proxy потрібно вимкнути буферизацію SSE й дозволити довгі з’єднання. Коли потік недоступний, панель використовує опитування та повторює підключення. Звіти оновлюються окремо, приблизно кожні 15 с; це не миттєвий потік енергії.

У «Зв’язок» є сканування локальної IPv4-підмережі /24 або меншої (до 256 адрес) у RFC1918-діапазонах. Перевіряються лише TCP-порти 502 та 8899. Пошук виконується **на локальному сервері**, не в браузері. Мережа іншого будинку має бути доступна серверу через налаштований VPN або маршрутизацію. Браузер не може сканувати сторонні домогосподарства через інтернет.

Результат — кандидат, а не підтверджений інвертор: модель, логер і карту регістрів потрібно перевірити. Кандидат 502 може бути доданий як домогосподарство. Порт 8899 позначає можливий Solarman V5; додайте об’єкт, вкажіть режим Solarman V5 та SN логера. Сам порт ще не підтверджує сумісність. Знайденим пристроям не надсилаються Modbus-записи. Новий об’єкт створюється з порожнім профілем, без дозволу запису.

До 64 профілів об’єктів зберігаються на сервері; обрати активний можна списком угорі. У кожного — власні IP, регістри, батареї, межі SOC і графік. Історія та звіти фільтруються за об’єктом. **Сервер продовжує фоновий збір неактивних Modbus TCP-об’єктів (до 8 одночасних читачів), щоб перемикання не зупиняло їхню історію.** Вибір активного об’єкта й налаштування глобальні для клієнтів одного сервера. Незалежні користувацькі ролі в цій версії не реалізовані. Для безперервного незалежного моніторингу кількох будинків можна запускати окремий сервер на кожному, з окремими HTTPS-адресами й каталогами даних; поточне підключення змінюється у «Зв’язок».

## Енергія через батарею

Зі знакового каналу `battery_w` окремо інтегруються `battery_charge_kwh` (увійшло в батарею з усіх джерел) та `battery_discharge_kwh` (вийшло з батареї). Додатне значення потужності означає заряд, від’ємне — розряд. Результат належить стороні вимірювання регістра (DC або AC за документацією), тому без уточнення втрат ці числа не тотожні енергії навантаження. Показники не додаються до прямого сонячного споживання повторно. Без `battery_w` обидва лічильники невідомі. Демо показує і заряд, і розряд на синтетичному добовому профілі. Походження заряду (сонце чи мережа) не розрізняється без додаткових каналів.

Окрім модульних перевірок, виконано наскрізну перевірку мобільного браузера із TCP-симулятором Modbus: авторизація/CORS, отримання реальних за форматом показників через SSE, команда SOC і контрольне читання, блокування команди після переходу офлайн. Фізичний Deye і Solarman не підключалися.

## Перевірка Solarman V5 на Windows

На комп’ютері біля інвертора, у каталозі завантаженого репозиторію:

```powershell
py -m pip install -r gateway/requirements.txt
py gateway/probe_solarman.py --host IP_ЛОГЕРА --serial SN_ЛОГЕРА
```

Замініть IP_ЛОГЕРА та SN_ЛОГЕРА власними значеннями, SN береться з етикетки логера, не з етикетки інвертора. Пароль Wi-Fi для V5-запиту не потрібен. Перевірка виконує тільки читання FC03 регістрів 0–9, показує сирі значення та не змінює конфігурацію. Успішна відповідь підтверджує V5-обмін, а не достовірність усієї карти регістрів чи дозвіл запису. За потреби задайте `--unit`, `--start`, `--count` (до 40). Інструмент запису не має.

У PWA в серверному профілі оберіть Solarman V5, порт 8899 та SN. Драйвер відкриває й закриває з’єднання для кожної операції, тому на повільному логері фактичний період телеметрії може перевищувати 2 с. Запис залишається заблокованим без перевіреної карти й явного дозволу. Підтримка API бібліотеки перевірена модульними тестами; фізичне V5-обладнання в середовищі розробки недоступне.

### Автоматичне встановлення Windows

`install-windows.ps1` приймає `-LoggerHost` і `-LoggerSerial`, за потреби встановлює Python через офіційний пакет winget, створює окреме venv, завантажує цей репозиторій та запускає тільки перевірку читання. Код і залежності зберігаються у `%LOCALAPPDATA%\DeyeControl`, звіт — `connection-check.txt`. Існуюча конфігурація зберігається. Невідомі регістри не заповнюються, запис не вмикається. Скрипт також створює `Start-DEYE.ps1` для локального сервера; той запитує пароль локально і не зберігає його на диску. Автозапуск, VPN і публічний доступ автоматично не створюються. Установник перевірено статично; виконання на Windows користувача ще потрібне.

### Готовий профіль читання Deye SUN-12K-SG04LP3-EU

Додано `gateway/profiles/deye_sg04lp3_readonly.json`: SOC 588, генерація PV1+PV2 672/673, стан мережі — біт 2 регістра 552, потужність батареї 590, потік мережі low/high 625/690, споживання low/high 653/659. Батарейна потужність перетворюється в прийняту додатну для заряду. Джерела: [Deye MODBUS RTU V105.1](https://github.com/user-attachments/files/16798469/MODBUS.RTU.V105.1-20231006.pdf) і [профіль ha-solarman Deye P3](https://github.com/davidrapan/ha-solarman/blob/main/custom_components/solarman/inverter_definitions/deye_p3.yaml). Профіль розрахований на LV трифазний пристрій типу 5; масштаб HV-виробів відрізняється.

`configure_deye.py --host IP --serial SN --apply` перевіряє тип пристрою, читає серійний номер і діапазони телеметрії, перевіряє фізично правдоподібні межі та записує **тільки локальну конфігурацію** із заблокованими командами. Перед заміною наявної конфігурації створюється резервна копія. Показники слід порівняти з дисплеєм Deye. Без `--apply` конфігурація не змінюється. `--expected-inverter-serial` дозволяє звірити конкретний пристрій. Для невідомих/невідповідних показників скрипт припиняє налаштування.

На встановленому Windows можна використати `connect-windows.ps1 -LoggerHost IP -LoggerSerial SN -ExpectedInverterSerial INVERTER_SN`: оновить код, виконає перевірку профілю, запустить локальний сервер та відкриє панель на цьому ПК. Випадковий пароль сервера діє в межах цього запуску й передається лише локальній панелі у URL-фрагменті, який одразу видаляється з адресного рядка; він не передається GitHub. Не копіюйте посилання з таким фрагментом іншим людям. Сервер прив’язаний до 127.0.0.1; для телефона й інтернету ще потрібен окремий HTTPS/VPN-доступ. Налаштування інвертора не змінюються.

Драйвер читання також підтримує `address_high` для 32-бітного low/high, `bit` для біта, `sum_addresses` для суми та `clip: positive/negative` для розділення напрямів. Такі складені поля не можуть мати `writable: true`. Пряме сонячне споживання в готовому профілі не вигадується й залишається невідомим без підтвердженого розрахунку потоків.

### Стабільне опитування Solarman

Поточна версія використовує одне V5-з’єднання за цикл, читає лише потрібні окремі регістри без проміжків і повторно використовує вже прочитані значення для імпорту/експорту. Паралельні читання й команди для одного логера серіалізовані. При помилці з’єднання закривається; наступний цикл створює нове. Дані попереднього циклу не видаються за нові. Панель окремо показує доступність SSE-сервера та помилку читання інвертора. Після оновлення код слід перезапустити на локальному ПК; публікація GitHub сама не замінює запущений сервер.

### Відновлення після невдалого повторного підключення

`connect-windows.ps1` перед перевіркою завершує лише процеси Python із точним шляхом до `%LOCALAPPDATA%\DeyeControl\source\gateway\app.py`, щоб старий сервер не займав логер і порт 8080. Інші Python-програми не завершуються. Перевірка читання повторюється до трьох разів зі свіжими з’єднаннями; після першого збою читає тільки необхідні слова замість великих блоків. Помилка містить тип винятку та адресу регістрів навіть для `TimeoutError()` без тексту. Детальний локальний звіт — `%LOCALAPPDATA%\DeyeControl\live-connection-check.txt`. Якщо перевірка не вдалася, поточний config не замінюється й запис в інвертор не виконується.


За результатом перевірки встановленого логера великі блоки іноді завершувалися `Empty()`, тоді як окремі слова читалися успішно. Тому діагностика й постійне опитування тепер використовують однакові одиночні читання, спільне V5-з’єднання на цикл і кеш повторюваних адрес. Це не збільшує поріг застарілості й не приховує збоїв; причина містить адресу конкретного регістра. Показники слід перевірити після перезапуску сервера на обладнанні.

### Режим paced-retry-2

Оскільки таймаути спостерігалися також на різних одиночних регістрах, додано спільний для діагностики й сервера `PacedReader`: пауза щонайменше 0.5 с між читаннями, до 3 спроб невдалого регістра та свіже з’єднання після збою з паузою 1.5/3 с. Уже прочитані слова в межах циклу не перечитуються. Повторення стосується **лише читання**, а не команд запису. Автоматичне налаштування встановлює інтервал опитування 10 с; фактичний цикл може бути довшим при таймаутах. Час зразка позначає початок збору, а `collection_seconds` — його тривалість. Пороги застарілості не збільшено. Панель відрізняє серверний потік від інтервалу логера. Це перевірене тестами виправлення, яке ще потребує перевірки на встановленому обладнанні.


### framed-transport-3 та автоматична перевірка

Додано адаптер для **pysolarmanv5 3.0.6**: накопичує TCP-фрагменти до повної V5-рамки, розділяє склеєні рамки, відкидає службові пакети й перевіряє V5-контрольну суму. Бібліотека далі перевіряє Modbus CRC, sequence, серійний номер і відповідь. Очікування відповіді активується до відправлення, щоб швидка відповідь не відкидалася через гонку потоків. Залежність закріплена, оскільки адаптер використовує внутрішній інтерфейс приймача. Джерело реалізації інтерфейсу: [pysolarmanv5](https://github.com/jmccrohan/pysolarmanv5). Наявність цього дефекту обробки TCP не доводить, що саме він спричинив усі таймаути фізичного логера.

Пройшли TCP-тести зі справжньою бібліотекою 3.0.6 і локальним симулятором: фрагментована відповідь, службовий пакет разом із відповіддю та швидкі відповіді. Для їх повторення встановіть `gateway/requirements.txt`, потім `python -m unittest discover -s tests -v`. Без залежності TCP-тести будуть явно пропущені.

Установник після відкриття панелі 30 секунд спостерігає `/api/status`, рахує різні часові мітки реальних вимірювань і зберігає `%LOCALAPPDATA%\DeyeControl\stability-check.json` без пароля/заголовків авторизації. `LIVE CHECK PASSED` означає лише щонайменше дві різні точки під час короткої перевірки, не гарантію довготривалої стабільності. Файл залишається локальним, автоматично нікуди не надсилається.

### utf8-config-4: кодування конфігурації Windows

У старих збірках `Path.write_text()` використовував типове кодування Windows (наприклад Windows-1251), тоді як скрипт налаштування очікував UTF-8. Через це після успішного читання інвертора могла виникати `UnicodeDecodeError` під час завантаження локального config.json. Тепер усі записи конфігурації явно UTF-8. Читання підтримує UTF-8, UTF-8 з BOM та старий Windows-1251; при наступному збереженні поля зберігаються у UTF-8. Перед застосуванням профілю залишається побайтова резервна копія старого файлу. Некоректний JSON не перезаписується автоматично. Тести перевіряють українську адресу, збереження параметрів і відсутність перезапису пошкодженого файлу.

### Наскрізна перевірка відновлення

`tests/test_recovery_integration.py` запускає окремі процеси налаштування й сервера з реальною бібліотекою pysolarmanv5 та TCP-симулятором. Початковий config.json містить українську назву в Windows-1251. Тест перевіряє побайтову резервну копію, перехід у UTF-8 без втрати полів, вимкнений запис та отримання двох різних часових міток телеметрії. TCP-відповіді навмисно розділені на фрагменти. Перевірка пройшла; вона відтворює формати даних і транспорт, але не є виконанням PowerShell на фізичному Windows чи перевіркою конкретного домашнього логера.

Запуск: `python -m unittest discover -s tests -p test_recovery_integration.py -v` після встановлення `gateway/requirements.txt`.

### local-session-5: оновлення вкладки після запуску

Локальний запуск тепер обмінює одноразово переданий пароль на випадкову HttpOnly-cookie з SameSite=Strict і Path=/api. Cookie приймається сервером лише від loopback-клієнтів і не містить пароля; після перезапуску сервер має новий токен. Це дозволяє оновлювати локальну сторінку та відкривати інші вкладки без втрати входу. Чинна cookie має пріоритет над застарілим Basic-заголовком старої вкладки. Для підключення GitHub PWA до зовнішнього сервера як і раніше використовується введений пароль у пам’яті вкладки; віддаленим клієнтам локальна cookie доступу не дає.

API повертає зрозумілий JSON 401 без браузерного Basic-діалогу. Вихід видаляє cookie поточного браузера. Помилки звітів і списку об’єктів не вимикають підтверджений стан телеметрії.

Браузерна перевірка `tests/browser_local_session.cjs` (Playwright/Chromium, окремий тестовий сервер) перевіряє старт через URL-фрагмент, HttpOnly, перезавантаження без фрагмента, другу вкладку, старий Basic-заголовок та вихід. Усі ці сценарії пройшли на локальному симуляторі; на ПК користувача потрібно перезапустити програму новою збіркою.
